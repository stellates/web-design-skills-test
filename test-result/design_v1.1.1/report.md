## v1.1.1で意図した改善

v1.1.0では、見た目とページ構成は改善した一方で、Bulma / Bulmaswatchを利用しているにもかかわらず、テーマ由来の色、罫線、文字表現、box相当の外観等を独自CSSで再実装する傾向が確認された。

特にMinty指定時には、テーマ自体の切り替えには成功したものの、Mintyらしい色や外観を独自CSS側でも大量に再定義していた。

v1.1.1では、この「テーマの再実装」を抑えるため、以下を強化した。

- Bulma / Bulmaswatch標準の色・タイポグラフィ・コンポーネント外観を優先する
- button、table、box、card、panel等を独自CSSで作り直さない
- テーマ色をHEX値で再定義しない
- 独自CSSはページ固有のレイアウト、レスポンシブ、状態表現等に限定する
- 大規模なテーマ変更が必要な場合は、単発HTMLへの大量上書きではなくSassカスタマイズを別工程として扱う

## 比較

### CSS実装

v1.1.0では、独自CSSがページ構成だけでなく、色、背景、罫線、文字サイズ、box相当の外観等にも広がっていた。

v1.1.1では、Bulma / Bulmaswatch標準クラスの利用が増え、独自CSSは明確に減少した。

この点は改善と評価できる。

一方で、標準コンポーネントへ寄せる指示が強く働いた結果、必要な画面固有の調整まで抑制された可能性がある。

したがって、今回の結果は「独自CSSを減らせば良い」のではなく、独自CSSの責務を適切に限定する必要があることを示している。

### 見た目

v1.1.0は、Bulma / Flatlyを基盤にしながらも、サイドバー、KPI、セクション境界、情報密度等に画面固有の調整が入り、初回生成物としての完成感が高かった。

v1.1.1は、構成自体は維持されているものの、Bulma標準コンポーネントの見た目が前面に出た。

結果として、保守性は高そうに見える一方、画面としての個別最適や仕上がりは弱くなった。

### 不要なラベル

v1.1.1のSkillには「不要なラベル・説明文を増やさない」という方針が含まれている。

しかし、実際の出力ではサイドバーに `MAIN`、`SYSTEM` といった補助ラベルが追加された。

これは、Skill内に指示が存在していても、他の強く反復された指示へモデルの注意が偏ることで、別の指示への追従が弱まる可能性を示す観察として扱う。

## Skill自体に見えた課題

### 1. 重複指定が多い

v1.1.1では、独自CSS抑制に関する同趣旨の指示が複数箇所に存在する。

例えば以下の内容が、独自CSS方針、テーマカスタマイズ、実装順序、最終確認、出力ルール等で繰り返されている。

- Bulma / Bulmaswatch標準を優先する
- 標準で実現できるものを独自CSSで再実装しない
- テーマ色を独自CSSで再定義しない
- 独自CSSは必要な場合だけ使う

人間にとっては補強説明だが、生成AIに対しては特定の制約だけを過度に強調する結果になる可能性がある。

今回の出力がBulma標準部品へ強く寄ったことからも、重複指示は単なる冗長性ではなく、生成結果へ影響する要素として検証する必要がある。

### 2. Skillが長くなりすぎている

v1.0.0以降、検証で見つかった問題をその都度Skillへ追加してきた。

その結果、Skillが「実装時に必要な最小限の指示」ではなく、「過去に発見した問題と対策を蓄積する文書」に近づいている。

Skillが長くなるほど、以下の懸念がある。

- 重要な指示と補助的な指示の優先順位が分かりにくくなる
- 同じ内容の反復によって一部指示が過剰に強くなる
- 本来重要な別の指示が相対的に弱くなる
- モデルが個々の禁止事項を満たす局所最適へ寄りやすくなる

知見は `report.md` に残し、Skill自体は実行時に必要な原則だけへ圧縮する方針が適切と考える。

### 3. 達成目的が曖昧になっている

Skill冒頭では、情報構造・操作性・可読性を持つ扱いやすいUIを目的としている。

一方、本文では独自CSSを避けること、標準コンポーネントを利用すること、禁止表現を避けること等、手段に関する指示が非常に多い。

結果として、AIにとって達成しやすい目的が「良いUIを作ること」ではなく、「独自実装を避けること」へ置き換わる可能性がある。

今後は、例えば以下のように目的をより明確にする必要がある。

**Bulma / Bulmaswatchを基盤として保守しやすさを保ちながら、初回生成の時点で実用的かつ十分に整ったUIを作る。**

そのうえで、CSSや装飾に関する指示は、この目的を達成するための最低限の原則として記述する方がよい。

### 4. 禁止事項が多すぎる

Skillには、SF風、AIサービス風、crypto dashboard風、グラデーション、ネオン、発光、ガラスモーフィズム、宇宙風背景、巨大ヒーロー、不要なアニメーション、過剰なカード化等、多数の禁止・抑制事項が列挙されている。

これらは過去の生成結果から得られた知見としては有用である。

しかし、すべてを実行用Skillへ保持する必要があるとは限らない。

例えば、以下のような少数の原則へ集約できる可能性がある。

- 要件と関係のないAI SaaS的・未来的な装飾を追加しない
- 情報より装飾を目立たせない
- 小要素を無意味にカード化しない
- 画面を見れば分かる説明を重複して追加しない

具体的な失敗例やアンチパターンの一覧は、Skillではなくreportへ残す方が役割分担として自然である。

## 今回得られた重要な観察

### 1. CSS暴走対策自体は機能した

v1.1.0で問題となった「テーマを独自CSSで再実装する」傾向は大きく減少した。

標準コンポーネントやhelper classが積極的に利用され、独自CSSの責務も比較的明確になった。

### 2. 制約を強めると別の局所最適が発生する

独自CSSを抑えた結果、今回はBulma標準コンポーネントへ寄りすぎた。

v1.0.0では装飾抑制によって画面が平坦になり、v1.1.1ではCSS抑制によってテンプレート感が強くなった。

単純な禁止や制約追加では、別方向の過剰適応を招く可能性がある。

### 3. 画面品質を支える独自CSSも存在する

v1.1.0で使用されていた独自CSSのすべてが不要だったわけではない。

テーマの再実装に該当するCSSは削減すべきだが、余白、配置、密度、境界、サイズ等の画面固有調整は、完成度向上に寄与していた。

今後は「独自CSSの有無」ではなく、「独自CSSが何を担当しているか」を判断基準とする必要がある。

### 4. Skillは知見置き場ではない

検証で得られた詳細な知見、失敗例、アンチパターン、仮説はreportへ蓄積する。

Skillには、それらから抽出した少数の実行原則だけを残す。

今後の改善は、Skillへのルール追加ではなく、不要な説明や重複指定を削減する方向を優先する。

## 今後の改善方針

次版では、v1.1.1へさらにルールを追加するのではなく、Skill全体を圧縮する。

主な方針は以下。

- Skillの達成目的を冒頭で一文に明確化する
- 同趣旨の指示は一箇所に統合する
- 禁止事項の具体例を大幅に減らす
- 詳細なアンチパターンや検証知見はreportへ移す
- CSS方針は「標準を基盤とする」「再実装しない」「画面固有の仕上げには必要最小限使ってよい」程度へ簡潔化する
- レイアウトは画面要件テンプレート側で指定し、Skill側では必要以上に扱わない
- 最終確認項目も本当に重要なものだけへ絞る

## 現時点の結論

`design_v1.1.1.md` は、v1.1.0で確認された独自CSSの増加、とくにBulmaswatchテーマ外観の再実装を抑える点では効果があった。

一方で、制約を詳細かつ重複して記述した結果、Bulma標準コンポーネントへの寄りが強くなり、v1.1.0より画面の完成感が低下した。

今回の問題は、CSSルール単体ではなく、Skillそのものが長くなり、同趣旨の指示や禁止事項を抱えすぎていることにも原因がある可能性がある。

今後は、検証で得られた知見をSkillへ追加し続けるのではなくreportへ残し、Skillは以下の役割に限定する。

**少数の原則で、AIを望ましい実装方向へ誘導する。**

次版では「さらに細かく制御する」より、「目的を明確にして指示を削る」ことを主な改善テーマとする。
