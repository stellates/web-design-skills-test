# 検証レポート 2026/8/29

## 利用したSKILL

`design_v1.0.0.md`

## 画面要件

```text
次のWEB画面を作ってください。

- WEBサイト名
  - Using AI Dashboard
- 概要
  - 利用中AIサービスの稼働状況（障害有無）、最新情報、使用量を見える化するダッシュボード
- 機能性
  - 利用中のAIサービスごとの各種情報が一画面で確認できる
  - リアルタイム同期
```

Skillを使用する場合は、上記プロンプトの2行目に以下のURLを追記した。

```text
https://github.com/stellates/web-design-skills-test/blob/main/skills/design_v1.0.0.md
```

それ以外の画面要件は同一として比較した。

## 出力結果

### Skill未使用版

- `preview_no_skill.html`
- Bootstrap 5をCDNから読み込み
- Bootstrap Iconsを使用
- 左サイドバー + 上部バー + KPIカード + サービス一覧 + リアルタイムイベント + 最新情報、という一般的な管理ダッシュボード構成
- 独自CSSを比較的多く使用
- 稼働状況、使用量、最新情報を視覚的に整理しており、完成時点の見栄えは良い

### Skill使用版

- `preview_use_skill.html`
- Skillの指定どおりBulma + Bulmaswatch FlatlyをCDNから読み込み
- Bootstrap Iconsを使用
- サービス一覧を画面の主役とし、右側に全体状況と更新情報を配置
- 独自CSSは状態ドット、使用量バーなど必要な箇所に限定
- 不要なカード、装飾、巨大な見出し等を避け、比較的素直な情報構造になっている

## 比較

### 見た目

今回の出力だけを見ると、Skill未使用版の方が第一印象は良い。

サイドバー、KPIカード、テーブル、イベント欄など、一般的なSaaS管理画面として見慣れた構成に自然にまとまっており、情報量が多いにもかかわらず画面としての完成感がある。

対してSkill使用版は、派手な装飾やカードの多用を抑え、サービスごとの状態確認を中心とした構成になっている。その分、画面としてはやや地味で、完成時点の「見栄え」だけを比較するとSkill未使用版に分がある。

少なくとも今回のケースでは、画面の見た目そのものについてはAIに大きく裁量を持たせた方が良い結果になったと言える。

### 情報構造

Skill未使用版は、要件からかなり積極的に画面構造を補完している。

例えば以下は元の要件には明示されていない。

- 左サイドバー
- 監視中サービス数などのKPI
- 推定利用額
- リアルタイムイベント
- サービス絞り込み
- 「すべて見る」等の操作

これらはダッシュボードとして自然であり、結果的に画面の完成度を高めている。一方で、要件にない機能や情報までAIが推測して追加しているとも言える。

Skill使用版は、要件にある「サービスごとの稼働状況・使用量・最新情報を一画面で確認する」という目的に比較的忠実であり、AIによる勝手な機能追加は少ない。

### 保守性

保守観点ではSkill使用版の方が若干有利に見える。

理由は、使用技術と実装ルールが明示的に固定されているためである。

- Bulmaを使用する
- Bulmaswatchのテーマを使用する
- Bootstrap Iconsを使用する
- CDNを基本とする
- JavaScriptフレームワークを不要に導入しない
- Bulma標準コンポーネントを優先する
- 独自CSSを最小限にする
- 不要なカードや装飾を増やさない

このようなルールがあることで、別画面を追加した場合や、別のAI・別セッションで実装した場合でも、技術選定やUI構造が一定方向へ収束しやすい。

Skill未使用版は今回かなり良い出力になったが、Bootstrapを選ぶことも、サイドバー型のレイアウトにすることも、独自CSSの書き方も、その場のAI判断に依存している。同じ要件を再生成した際に同じ設計思想になる保証はない。

したがって、Skillの効果は「単発で最も見栄えの良い画面を生成すること」よりも、「複数画面・複数回の生成において実装方針を揃え、後から扱いやすくすること」にある可能性が高い。

## 気になった点

### Skill未使用版でもBootstrapを採用している

今回もっとも気になる点。

Skill未使用版でも、AIは自発的に以下をCDNから読み込んでいる。

- Bootstrap 5
- Bootstrap Icons

つまり、Skill使用版だけが既存CSSフレームワークを採用したわけではない。

むしろSkill未使用版も、素のHTML/CSSを一から設計するのではなく、最初からBootstrapを基盤として画面を組み立てている。これが未使用版の完成度を大きく押し上げている可能性がある。

今回の検証以前の会話では、Web画面作成時に既存CSSフレームワークやCDNを利用する方針について何度かやり取りしている。そのため、Skillを明示していない場合でも、会話履歴やメモリ等のコンテキストが出力に影響した可能性は否定できない。

ただし、この結果だけから原因を特定することはできない。

考えられる要因としては、少なくとも以下がある。

- 過去の会話内容が影響した
- 保存されたメモリ等が影響した
- モデル自身がダッシュボード生成時にBootstrapを選択しやすい
- その他のコンテキストが影響した

そのため、今回の結果は厳密には「完全に独立したSkill有無の比較」とは言い切れない。

## 現時点の評価

初回検証としては、Skillの有無で明確に性格の異なる画面が生成された。

Skill未使用版はAIの裁量が大きく、要件を膨らませながら完成度の高い管理画面に仕上げている。単発の画面生成として見ると、今回はこちらの方が好印象だった。

Skill使用版は見た目の派手さでは劣るものの、指定した技術・デザイン方針にかなり忠実であり、実装の予測可能性が高い。特に複数画面を継続して作る場合や、後から人間が保守する場合には、この制約がメリットになる可能性がある。

現時点では、以下のように整理できる。

| 観点 | Skill未使用 | Skill使用 |
| --- | --- | --- |
| 第一印象・見栄え | 良い | やや地味 |
| AIによる提案力 | 高い | 制約される |
| 要件への忠実さ | やや拡張的 | 高い |
| 技術選定の予測可能性 | 低い | 高い |
| 独自CSSの抑制 | 弱い | 強い |
| 継続開発時の統一性 | 不明 | 期待できる |
| 保守性 | 良い可能性はあるが出力依存 | 若干有利に見える |

## 今後の検証課題

今回だけでは、Skillによる効果とモデル側の既存コンテキストによる効果を十分に分離できていない。

今後は、同じSkillを固定したまま異なる種類の画面を複数生成し、以下を継続して確認したい。

- Skill使用時に画面間のデザイン・実装方針が安定するか
- Skill未使用時にCSSフレームワークや画面構成がどの程度ばらつくか
- Skillの制約が強すぎて、AIの良い提案まで潰していないか
- 独自CSS量やHTML構造が、修正を重ねた際の保守性にどう影響するか
- 新しい会話やコンテキストの少ない環境でも、Skill未使用版がBootstrap等を自発的に採用するか

特に最後の点は、今回の比較結果を評価するうえで重要である。

Skillの目的を「毎回同じ見た目を生成させること」ではなく、「AIに任せる範囲と、人間側で固定したい実装原則の境界を探すこと」と捉え、今後の結果を蓄積していく。
