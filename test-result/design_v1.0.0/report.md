# 検証レポート 2026/8/29 ver1.0.0

## 実行条件

* 利用したSkill: `design_v1.0.0.md`
* モデル: GPT-5.6 Sol
* 思考レベル: 中程度
* 実行環境: ChatGPT（Webブラウザ）
* 実行方法: 後述の画面要件のプロンプトを実行する

### 補足情報

* Skill未使用版の初回生成は、最初はメモリ参照が有効な設定の「新しいチャット」で生成した。
* そのため、過去の会話内容や保存されたコンテキストが生成結果へ影響した可能性がある。
* この影響を確認するため、２回目のSkill未使用生成については一次チャット（過去の通常チャット履歴を引き継がない状態）でも再実行した。
* 一次チャットでの再試行結果は `preview_no_skill_retry.html` として保存している。
* なお、ChatGPT内部でどのコンテキストが実際に生成へ影響したかを厳密に特定することはできないため、本レポートでは実行環境および観測可能な条件のみを記録する。

## 画面要件

```text
次のWEB画面を作ってください。

- WEBサイト名
  - Using AI Dashboard
- 概要
  - 利用中AIサービスの稼働状況（障害有無）、最新情報、使用量を見える化するダッシュボード
- 機能性
  - 利用中のAIサービスごとの各種情報が一画面で確認できる
  - リアルタイム同期
```

Skillを使用する場合は、上記プロンプトの2行目に以下のURLを追記した。

```text
https://github.com/stellates/web-design-skills-test/blob/main/skills/design_v1.0.0.md
```

それ以外の画面要件は同一として比較した。

- `preview_no_skill_retry.html`

## 出力結果

### Skill未使用版（初回）

`preview_no_skill.html`

- Bootstrap 5をCDNから読み込み
- Bootstrap Iconsを使用
- 左サイドバー + 上部バー + KPIカード + サービス一覧 + リアルタイムイベント + 最新情報、という一般的な管理ダッシュボード構成
- 独自CSSを比較的多く使用
- 稼働状況、使用量、最新情報を視覚的に整理しており、完成時点の見栄えは良い
- AIが要件を積極的に補完し、一般的なSaaS管理画面として完成度の高い構成になった

この出力単体では、Skillを利用しなくても既存CSSフレームワークとアイコンライブラリを自発的に採用しており、当初想定していた「Skillなし」の典型例とは異なる結果になった。

### Skill未使用版（再試行）

`preview_no_skill_retry.html`

初回の未使用版とは大きく異なる結果になった。

主な特徴は以下。

- CSSフレームワークを使用せず、独自CSSで画面全体を構築
- ダークテーマを採用
- 紫・青系のアクセントカラーを使用
- 背景にradial-gradientを使用
- ロゴ、ボタン、使用量バー、グラフ等にgradientを多用
- backdrop-filterによる半透明表現を使用
- 大きめの角丸、影、カードを多用
- KPIカードを4枚配置
- サイドバー型ナビゲーションを配置
- 使用量グラフ、インシデント表示など、要件から追加要素を積極的に補完
- Bootstrap Icons等のアイコンライブラリは使用せず、記号・文字をナビゲーション等に使用

見た目としては、近年のAIサービスやSaaS管理画面でよく見られるダーク・グラデーション中心のデザインになった。

これは、今回Skillで抑制しようとしているデザイン傾向にかなり近い。

また、HTML/CSS量も大きく、画面の基本構造だけでなくデザインシステム相当のCSSを生成物内に独自定義している。

### Skill使用版

`preview_use_skill.html`

- Skillの指定どおりBulma + Bulmaswatch FlatlyをCDNから読み込み
- Bootstrap Iconsを使用
- サービス一覧を画面の主役とし、右側に全体状況と更新情報を配置
- 独自CSSは状態ドット、使用量バー、サービスロゴ等の必要な箇所に限定
- 不要なカード、装飾、巨大な見出し等を避け、比較的素直な情報構造になっている
- 動的要素は必要な範囲のJavaScriptで実装
- 要件に含まれる「各サービスの状況を一画面で確認する」という目的が画面構造の中心になっている

## 比較

### 見た目

3出力はかなり性格が異なる。

#### Skill未使用・初回

一般的なBootstrapベースの管理画面としてまとまりが良く、第一印象も良い。

サイドバー、KPIカード、テーブル、イベント欄などを自然に組み合わせており、単発の初回生成物としては完成感が高かった。

#### Skill未使用・再試行

初回未使用版とは異なり、ダークテーマ、紫・青系のグラデーション、大きな角丸、影、半透明表現を中心とした強いデザインが生成された。

一見すると作り込まれているが、特定のSaaS・AIサービス風のデザイン傾向が強く、用途に関係なく同じ方向へ寄りやすい懸念がある。

また、画面固有のデザインを大量の独自CSSで実現しているため、同一システムの別画面を追加した際に同じ設計を安定して再現できるかは不明である。

#### Skill使用

派手さは抑えられているが、既存テーマを基盤としているため、画面全体のデザインルールが明確である。

Skill未使用・再試行版と比較すると装飾性は低いが、情報を読むためのUIとしては落ち着いている。

一方で、制約を強くすることで画面が地味になりすぎる可能性はあり、今後Skill側で「過剰装飾を防ぎつつ、無機質になりすぎない」バランスを調整する余地がある。

### 情報構造

Skill未使用版は、初回・再試行ともに要件から積極的に画面内容を補完している。

例えば以下は元の要件には明示されていない。

- 左サイドバー
- 監視中サービス数などのKPI
- 推定利用額・推定コスト
- リアルタイムイベントやインシデント表示
- 応答時間
- 利用量グラフ
- サービス絞り込みや追加操作

これらはダッシュボードとして自然な補完であり、AIの提案力が画面の完成度を高めている。

一方で、必要性を確認せずに画面要素を増やす傾向もある。

Skill使用版でも要件からの補完自体は行われているが、追加要素は比較的抑制され、サービスごとの稼働状況・使用量・更新情報を一画面で確認するという中心目的から大きく外れていない。

今回の結果から、SkillはAIの補完能力そのものを止めるのではなく、補完結果の表現方法や実装方法を一定範囲に制約する役割として機能しているように見える。

### 実装方針

Skill未使用の2回だけでも、技術選定が大きく変わった。

| 出力 | 主な実装方針 |
| --- | --- |
| Skill未使用・初回 | Bootstrap 5 + Bootstrap Icons + 独自CSS |
| Skill未使用・再試行 | フレームワークなし + 大量の独自CSS |
| Skill使用 | Bulma / Bulmaswatch + Bootstrap Icons + 必要最小限の独自CSS |

この差は重要である。

Skill未使用でも良い画面は生成できるが、「どの技術で、どの程度独自実装するか」は生成ごとのAI判断に委ねられる。

Skill使用時は、少なくとも今回の出力では指定した技術方針に収束している。

### 保守性・継続開発

保守性については、単一HTMLを眺めただけでは断定できない。

ただし、Skill未使用・再試行版では色、余白、角丸、影、カード、ナビゲーション、グラフ等を画面固有の独自CSSとして広く定義している。

この方法は単発画面の自由度は高い一方、別画面を生成するたびに似ているが微妙に違うデザインルールが作られる可能性がある。

Skill使用版では、既存フレームワーク・テーマと実装原則を先に固定しているため、複数画面・複数回の生成で設計方針を揃えやすいと考えられる。

したがってSkillの価値は、「単発で最も見栄えの良い画面を出すこと」だけではなく、生成を繰り返したときの予測可能性や統一性にもある可能性が高い。

## 初回Skill未使用版についての注意

初回のSkill未使用版では、AIが自発的にBootstrap 5とBootstrap Iconsを採用した。

今回の検証以前の会話では、Web画面生成時のCSSフレームワーク、CDN、Bootstrap、Bulma等について議論していた。

そのため、初回未使用版については、過去の会話内容や保存されたコンテキスト等が出力へ影響した可能性を否定できなかった。

当初考えられた要因は以下。

- 過去の会話内容が影響した
- 保存されたメモリ等が影響した
- モデル自身がダッシュボード生成時にBootstrapを選択しやすい
- その他のコンテキストが影響した

この疑問を残したまま初回出力を破棄せず、Skill未使用条件を別途再試行した。

その結果、`preview_no_skill_retry.html` ではBootstrap等は採用されず、独自CSSによるダーク・グラデーション中心の画面が生成された。

この結果は、「Skillなしなら必ずこのデザインになる」ことを意味しない。

むしろ重要なのは、同じ画面要件であってもSkill未使用時には、技術選定・デザイン方向・独自CSS量が大きく変化し得ることが実際に確認できた点である。

初回未使用版も再試行版も、どちらかを異常値として捨てるのではなく、両方をSkill未使用時の観測結果として保存する。

## 現時点の評価

初回検証と再試行を合わせると、評価は当初より変化した。

最初の2出力だけを比較した時点では、Skill未使用版の方が見栄えが良く、「AIに大きく裁量を持たせた方が良い画面になる」可能性も考えられた。

しかしSkill未使用条件を再試行すると、同じ要件から大きく異なる技術選定・デザインが生成された。

そのため、現時点では単純に「Skillありの方が良い」「Skillなしの方が良い」と評価するより、以下のように整理する方が適切である。

| 観点 | Skill未使用 | Skill使用 |
| --- | --- | --- |
| 単発での見栄え | 良い結果になる場合がある | 比較的安定するが地味になる場合がある |
| AIによる提案力 | 高い | 一定の制約を受ける |
| 要件からの補完 | 積極的 | 必要範囲に収まりやすい |
| デザイン方向 | 出力ごとの差が大きい | Skillの方針へ収束しやすい |
| 技術選定 | 出力ごとの差が大きい | 予測しやすい |
| 独自CSS量 | 大きくなる場合がある | 抑制されやすい |
| 継続開発時の統一性 | 生成ごとの確認が必要 | 期待できる |
| 初回生成物の安定性 | 高いとは言い切れない | 今回は比較的高い |

## 今回得られた重要な観察

### 1. Skill未使用でも良い画面は生成できる

Skillは「Skillなしでは良いUIを作れない」ことを前提にするものではない。

初回未使用版のように、AIの裁量だけで完成度の高い画面が生成されるケースはある。

### 2. Skill未使用時の出力は技術選定から変動する

今回、同一要件でBootstrapベースの画面とフレームワークなしの画面の両方が生成された。

見た目だけでなく、実装基盤そのものが変化した。

### 3. SkillはAIの創造性を完全に止めるものではない

Skill使用版でも、要件からサービス一覧、詳細表示、状態集計、更新情報等を補完している。

制約しているのは主にデザイン・技術上のガードレールであり、情報設計の補完能力はある程度維持されている。

### 4. 比較では「良い結果だけを採用しない」ことが重要

初回未使用版だけを採用すると「SkillなしでもBootstrapを自然に選び、良い管理画面を作れる」という結果になる。

再試行版だけを採用すると「SkillなしではAI SaaS風のデザインへ暴走する」という結果になりかねない。

実際には両方が生成されている。

そのため、このリポジトリでは複数回の結果を残し、生成の分布や揺らぎそのものを見る必要がある。

### 5. Skillの評価軸として再現性・予測可能性が重要

Skillの効果を評価する際、単一画面の美しさだけでは不十分である。

今後は、同じ条件で再生成したときに、技術選定・情報構造・デザイン原則がどの程度維持されるかを見る必要がある。

## 今後の検証課題

今回だけではSkillの有効性を断定できない。

今後は同じSkillを固定しながら、以下を継続して確認する。

- Skill使用条件でも複数回生成し、出力の揺らぎを確認する
- Skill使用時に画面間のデザイン・実装方針が安定するか
- Skill未使用時にCSSフレームワークや画面構成がどの程度ばらつくか
- Skillの制約が強すぎてAIの良い提案まで潰していないか
- Skillによって落ち着きすぎた、無機質な画面にならないか
- 不要なラベル、補助テキスト、カード等がどの程度抑制されるか
- 独自CSS量やHTML構造が、修正を重ねた際の保守性にどう影響するか
- 業務ダッシュボード以外の画面でも同様の効果が出るか
- 異なるSkillバージョン間で何が改善・悪化したか

また、生成時のチャット条件・モデル・利用Skill・追加指示など、結果へ影響し得る条件は可能な範囲で記録する。

## 現時点の結論

`design_v1.0.0.md` の初回検証では、Skillを使用することで「最も派手で見栄えのする画面」が生成されたとは言えない。

一方で、Skill未使用の再試行によって、同一要件でも技術選定とデザイン方向が大きく変化することが確認できた。

このため、Skillの役割は単純なデザイン品質向上ではなく、

**AIの情報設計・補完能力を利用しながら、技術選定とデザイン上のガードレールを与え、初回生成物の方向性を予測しやすくすること**

として評価するのが現時点では妥当である。

今後も良い結果・悪い結果の両方を残し、Skillの各バージョンが生成結果へ与える影響を継続して比較する。
