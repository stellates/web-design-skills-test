## 表示上のノイズと定型表現の再発

v1.1.2では、過去バージョンで抑えていた「それっぽく見せるための表示上のノイズ」も一部再発した。

### 英語表現の過剰な混在

画面要件は日本語であり、主要な説明も日本語で成立する画面であるにもかかわらず、以下のような英語表現が多数追加された。

- `Dashboard`
- `Connected services`
- `Service health`
- `Monthly requests`
- `Estimated cost`
- `AI Services`
- `Usage Trend`
- `OVERVIEW`
- `MANAGE`
- `Workspace`
- `Personal`

英語そのものを禁止する必要はないが、装飾的・雰囲気作りのために表示言語を混在させると、画面全体の一貫性が下がる。

今後は、固有名詞や一般的に英語表記が自然なものを除き、画面の主要言語に合わせて表記を統一する方がよい。

### 意味の薄い頭文字マーク・疑似ロゴ

サービス一覧では、`O`、`G`、`A`、`P` のような頭文字を視覚マークとして表示する実装が追加された。

これらは一覧にリズムを与える効果はあるが、正式なロゴでもなく、サービス名が隣接しているため情報価値は低い。

この種の疑似ロゴや頭文字マークは、AIが画面をそれらしく見せるために追加しやすい定型装飾と考えられる。

識別や操作に実際の意味があるアイコンは利用してよいが、装飾目的だけの頭文字・記号は原則として不要である。

### サイト名・画面名の重複

v1.1.2では、左上に `Using AI`、上部ヘッダーに `Using AI Dashboard` を表示しており、同一画面内でサイト名相当の情報が重複している。

さらに、一方だけ省略表記となっているため、同じものを指しているのか、ブランド名と画面名を分けているのかが曖昧である。

同じ名称や意味をサイドバー、ヘッダー、見出し等で必要なく繰り返すことは避け、表示する場合は役割と表記を統一する必要がある。

この問題は、単なる文字数削減ではなく、**同じ意味を別表現で重ねて画面をそれらしく見せるAI特有の補完を抑えること**として扱う。

## 要件外補完の問題

元の要件で求めている情報は、概ね以下である。

- 利用中AIサービスの稼働状況
- 最新情報
- 使用量
- 一画面で確認
- リアルタイム同期
- 左サイドバー + 上部ヘッダー + メインコンテンツ

一方、生成結果では以下のような要素が追加された。

- Connected services
- Service health
- Monthly requests
- Estimated cost
- Monthly budget
- Usage Trend
- Add service
- Connections
- Notifications
- Settings
- Workspace
- Personal
- 前月比や利用額等の具体的な数値

これらの多くは、ダッシュボードとしては自然であり、見た目の完成度にも寄与している。

しかし、画面要件として与えられていない業務概念、機能、指標、ナビゲーション項目までAIが発明している。

ここで重要なのは、「情報設計の裁量」と「要件の発明」を分けることである。

AIに任せたいのは、与えられた情報をどのように配置・グルーピングし、どの順序で見せるかという**表示上の情報設計**である。

一方、要件に存在しない機能、業務概念、データ項目、指標そのものを追加することまでは求めていない。

今後は、AIに残す裁量の種類をより明確に定義する必要がある。

## 「完成度」が暴走の口実になった可能性

v1.1.2では、目的として以下の趣旨を強くした。

- 初回生成の時点で実用的かつ十分に整ったUIを作る
- UIの完成度や使いやすさを高めるために必要な範囲で独自CSSを使用してよい

この方針自体は、v1.1.1のテンプレート感を脱するために必要だった。

実際、見た目は大きく改善している。

一方で、「完成度を高める」という目的が、以下の行動まで正当化する余地を与えた可能性がある。

- KPIを追加する
- 予算・利用額を追加する
- 利用推移グラフを追加する
- 管理機能を追加する
- サイドバー項目を増やす
- 独自CSSでパネル外観を作り込む
- 英語ラベルや疑似ロゴ等を追加して画面をそれらしく見せる

したがって、次版では「完成度を高める」という目的を削るのではなく、**何の範囲を整えてよいのか**を限定する方が適切と考える。

目標は、

**与えられた画面要件の範囲を維持したまま、見やすく実用的なUIへ整えること**

とするのが自然である。

これらのうち、固定サイドバー、レスポンシブ、一覧のgrid構造等はページ固有の実装として合理性がある。

一方、以下はBulma / Bulmaswatch側の責務と重なっている。

- パネル・カード相当の外観

- テーマ色
- 状態色
- 独自プログレスバー

Flatlyで用いられる色に近いHEX値を独自CSSへ直接記載する傾向も再発している。

したがって、v1.1.2では再び「Bulmaswatchを読み込んだ独自UI」に近づいた部分がある。

ただし、v1.1.1の結果からも分かる通り、単純に独自CSSを減らせばよいわけではない。

今回の画面品質を支えているのも、サイドバー幅、余白、境界、情報密度、カラムバランス等の画面固有調整である。

また、一般的なWebデザイナー／フロントエンドコーダーが単一画面として保守する前提では、v1.1.0やv1.1.2程度のHTML / CSS / JavaScriptは十分に許容範囲と考えられる。

問題はCSS量そのものではなく、画面数が増えた際の共通化や、Bulma / Bulmaswatchとの責務分担である。

今後の判断基準はCSS量ではなく、**独自CSSが何を担当しているか**とする。

整理すると、目指す方向は以下。

- 独自CSSは許容する
- 画面固有の構造・配置・レスポンシブ調整には利用してよい
- セレクタやクラス命名は単純で役割が分かる状態を保つ
- Bulma / Bulmaswatchが担う色・標準コンポーネント外観を大規模に再発明しない

## リアルタイム同期の扱い

生成結果では、JavaScriptによって一定間隔で同期状態を更新するデモ挙動が実装された。

しかし、今回の画面要件には実際のデータソースや同期APIは存在しない。

そのため、実際には同期していないにもかかわらず、一定時間ごとに同期処理を実行しているように見せる実装は、要件を満たしたというより**架空の実装で機能要件を満たしたように演出している**と評価できる。

データソースが存在しない初期UI生成では、以下のような扱いの方が自然である。

- 同期中・最終同期時刻等のUI状態を表現する
- 実際の同期処理は仮実装であることが分かる構造にする
- 根拠のない自動同期周期やデータ更新を勝手に確定しない

これはデザインSkill単独の問題ではないが、要件外補完の一種として記録する。

## 今回得られた重要な観察

### 1. 見た目の良さと要件遵守は別軸で評価する必要がある

v1.1.2は見た目としては成功している。

したがって、「暴走したからデザインも失敗」と評価してはいけない。

今回の問題は、デザイン品質ではなく、要件境界と実装責務の制御にある。

### 2. AIの裁量は有益だが、種類を限定する必要がある

AIの情報設計・レイアウト能力を強く抑えるとv1.1.1のようにテンプレート感が増える。

一方、裁量を広げすぎるとv1.1.2のように機能・データ・業務概念まで発明する。

今後は、AIの裁量を以下のように分ける必要がある。

許容したい裁量:

- 与えられた情報の配置
- グルーピング
- 優先順位
- 視線誘導
- 画面内の構成
- 必要な範囲の視覚的仕上げ

許容したくない裁量:

- 要件にない機能の追加
- 要件にないデータ項目・KPI・指標の追加
- 要件にない管理機能やナビゲーション項目の追加
- 実在しない同期処理等を完成機能として実装すること
- 雰囲気作りのためだけに表示言語を混在させること
- 情報価値のない疑似ロゴや頭文字マークを追加すること
- 同じ名称・意味を別表記で重複表示すること

### 3. 独自CSSは量ではなく責務で見る

v1.1.2の見た目の良さは、独自CSSによる画面固有の調整にも支えられている。

したがって、独自CSS自体を抑える方針へ戻す必要はない。

一般的な保守性という観点では、v1.1.0やv1.1.2のCSS量は単一画面なら十分に許容範囲であり、問題はフレームワーク・テーマとの責務分担と、複数画面へ展開した際の共通化である。

### 4. 「完成度」という抽象目標は範囲指定とセットにする必要がある

「十分に整ったUIを作る」という指示だけでは、モデルが情報や機能まで補って完成度を高めようとする可能性がある。

今後は、完成度を高める対象を「与えられた画面要件の範囲内」と明示する必要がある。

### 5. 表示上のノイズ抑制は復元候補である

v1.1.0からSkillを圧縮する過程で、表示言語の一貫性、意味のないマーク、名称重複等を抑える指示も弱くなった。

これらはCSSの細かい実装規則とは異なり、画面品質と情報の明瞭さに直接関係する。

次版では、以下のような少数の原則として復元する価値がある。

- 主要な表示言語を統一し、装飾目的で英語を混在させない
- アイコンや記号は識別・操作上の意味がある場合だけ使い、疑似ロゴや頭文字マークを追加しない
- 同じ名称・意味をサイドバー、ヘッダー、見出し等で不必要に繰り返さない

### 6. Skillは引き続き知見置き場にしない

今回得られた具体的な失敗例、英語表現、疑似ロゴ、名称重複、要件外補完の一覧、同期デモ問題、v1.1.0〜v1.1.2の比較等は、このreportへ残す。

次版Skillには、これらをすべて列挙せず、必要な実行原則だけを抽出する。

## 次版に向けた方向性

次版では、v1.1.0とv1.1.2の見た目の良さを維持しながら、必要なガードレールだけを復元する。

重点は以下とする。

1. 要件外の業務概念・機能・データを発明しない
2. 表示言語を不必要に混在させない
3. 情報価値のない疑似ロゴ・頭文字マークを追加しない
4. 同じ名称や意味を不必要に重複表示しない
5. 独自CSSは一般的な保守許容範囲として認めつつ、テーマ全体を大規模に上書きする設計は避ける

v1.1.1のようなCSS細則の大量追加には戻さず、v1.1.0から外しすぎた表示上・要件上のガードレールを選択的に復元する。

## 現時点の結論

v1.1.2は、Skillを圧縮してAIの設計能力を戻すという点では成功した。

見た目も非常に良く、現時点ではv1.1.0 Flatly版に次いで高く評価できる。

また、一般的なWebデザイナー／フロントエンドコーダーによる単一画面の保守という観点では、v1.1.0・v1.1.2程度のHTML / CSS / JavaScriptは過剰とは言いにくく、十分に許容範囲と考える。

一方で、AIの裁量範囲が明確でなかったため、画面の見せ方だけでなく、要件にない機能・データ・業務概念、英語ラベル、疑似ロゴ、名称重複まで補完対象になった。

したがって、次の改善目標は「もっとCSSを減らすこと」でも「禁止事項を大量に増やすこと」でもない。

**AIに残す裁量の種類を明確にし、v1.1.0から外しすぎた表示上・要件上のガードレールだけを復元すること**である。

見た目の方向性としては、v1.1.0とv1.1.2の良さを維持する。

実装上は、人間が保守できる範囲の独自CSSを許容しつつ、要件を発明せず、表示上のノイズを増やさない。

このラインをv1.1.x系列のFIX候補として検証する。
