## v1.1.0で意図した主な改善

v1.0.0では、AIによる装飾上の暴走を抑えるため、不要なカード、装飾、独自CSS、補助ラベル等を強く抑制していた。

その結果、技術選定とデザイン方向は安定した一方で、ページ全体の構図や情報のメリハリまで弱くなる傾向が見られた。

v1.1.0では、主に以下の方向へ調整した。

- ページ全体の情報構造・レイアウト設計にはAIの裁量を残す
- カードそのものを避けるのではなく、情報のまとまりを表現する用途では使用を許容する
- サイドバー、KPI、補助領域等も、画面上の役割が明確であれば使用を許容する
- Bulmaswatchテーマの色を意味のある箇所で活用する
- 独自CSSを全面的に避けるのではなく、画面構造・余白・罫線・レスポンシブ等のための限定的な利用を許容する
- 「迷ったら追加しない」の対象を主に装飾へ限定し、情報設計上必要な補完は許容する
- 不要なラベルは具体的な単語の禁止ではなく、意味の重複を避ける方向へ整理する

目標は、v1.0.0のガードレールを維持しながら、単調さを減らし、初回生成物としての完成感を高めることである。

v1.0.0 Skill使用版は、技術選定と装飾抑制は狙い通り機能した一方、画面が静かで平坦になり、管理ダッシュボードとしての情報密度や完成感が弱かった。

v1.1.0 Flatly版では、サイドバー、KPIサマリー、サービス一覧、補助情報を組み合わせ、v1.0.0 Skill未使用・初回版で良かった「一般的な管理画面としての構成力」に近づいた。

Minty版も見た目としては十分に完成しているが、Flatly版と比較するとサイドバーがなく、単一ページ型の情報ボードに近い構成となった。

現時点の主観評価では、継続利用する業務ダッシュボードとしてはFlatly版の構成の方が好ましい。

### 情報構造

v1.1.0では、AIによる情報設計の補完がv1.0.0 Skill使用版より積極的になった。

サイドバー、KPI、推定利用額、残り利用枠、最新情報、通知設定等、元要件にない要素を自然に補完している。

一方、Flatly版とMinty版でページの主要構成が大きく変化したことから、「レイアウトそのものをAIの裁量に任せる」場合の揺らぎも確認できた。

### カード・情報グルーピング

v1.1.0では、カードやボックスを情報のまとまりを表現するために使用している。

v1.0.0のようにカード自体を強く避けるのではなく、情報グループ単位で使用することで、平坦さを減らしつつ過剰なカード化も避けられている。

この方針はFlatly版・Minty版ともに概ね機能している。

### テーマカラーと視覚的メリハリ

Flatly版では、現在位置、同期状態、稼働ステータス、使用量、主要操作等にテーマ色が使われた。

Minty版でも同様に緑系の色へ切り替わり、テーマの雰囲気自体は適切に反映された。

この点では、テーマ指定による視覚的な切替は成功している。

## 独自CSSの追加検証

v1.1.0では、v1.0.0 Skill使用版より独自CSS量が増えている。

Flatly版では、固定サイドバー、ページ全体のレイアウト、KPI・セクションの境界、情報密度、レスポンシブ制御等に独自CSSを利用していた。

これらにはページ固有の構成を成立させるための合理的なものも多い。

一方、Minty版を追加検証したことで、別の課題が見えた。

Minty版ではテーマの色を正しく反映できているものの、Bulmaswatchのテーマをそのまま利用するだけでなく、Mintyに近い背景色、罫線色、文字色、状態色等を独自CSSで多数定義している。

つまり、テーマ変更時にFlatly用の固定色が残る問題は確認されなかったが、代わりに「AIが選択テーマを参考にして、テーマ風のデザインシステムを独自CSSで再実装する」傾向が確認された。

これは今後の保守性を考えると課題である。

独自CSSは量だけでなく責務で評価する必要があるが、以下は既存フレームワーク・テーマ側へ寄せたい。

- テーマ由来の基本色
- タイポグラフィ
- 標準的なボックス・パネル外観
- ボタン、テーブル等の標準コンポーネント外観
- 標準ユーティリティで表現できる余白・文字サイズ・文字色

一方、以下は独自CSSを許容してよい。

- ページ固有のレイアウト
- 固定サイドバー等、Bulma標準だけでは実現しにくい構成
- レスポンシブ時の配置・開閉制御
- サービス状態等の固有表現
- 画面要件上必要な狭い範囲の調整

### テーマカスタマイズの考え方

今後は「テーマを独自CSSで再実装しない」ことをより明確にする必要がある。

CDN利用を前提とした初期生成では、Bulma / Bulmaswatchの標準表現を優先し、大量の独自CSSでテーマを上書き・再構築しない。

テーマ自体を大きく変更したい場合は、初期HTML内で大量に上書きするのではなく、Sassを利用した正規のテーマカスタマイズを次段階の選択肢とする方が保守上自然と考える。

ただし、初回生成時にAIが勝手にSassやビルド環境を導入することは避ける。

整理すると、初期生成では以下を基本とする。

1. Bulma / Bulmaswatchの標準表現を使用する
2. ページ固有の不足部分だけ独自CSSで補う
3. テーマそのものを変更したくなった場合は、別工程としてSassカスタマイズを検討する

## レイアウトの揺らぎについて

Flatly版とMinty版では、同じ画面要件・同じSkillを利用したにもかかわらず、主要レイアウトが大きく変化した。

Flatly版は左サイドバーを持つ管理アプリ型の構成となった一方、Minty版はサイドバーを持たず、上部ヘッダーを中心とした単一ページ型の構成となった。

テーマの変更だけでレイアウトまで変化したことが直接の原因とは断定できないが、少なくとも現在のSkillではページ構成に一定の揺らぎが残ることが確認できた。

ただし、この問題をDESIGN Skill側で「ダッシュボードでは必ずサイドバーを使う」等と固定することは適切ではないと考える。

レイアウトはシステム・画面の要件に依存するため、デザイン上の一般ルールではなく要件として与える方が自然である。

今後は `DESIGN.md` 相当のデザインSkillとは別に、画面要件を整理するためのプロンプトテンプレートを用意し、その中に希望レイアウトを指定できる項目を設ける方向を検討する。

例として、以下のような情報を要件化することが考えられる。

- ナビゲーション方式
  - 左サイドバー
  - 上部ナビゲーション
  - ナビゲーションなし
  - AIに任せる
- ページ構成
  - 1カラム
  - メイン + サブカラム
  - ダッシュボード型
  - AIに任せる
- 情報密度
  - 高め
  - 標準
  - 低め
- 優先して表示する領域
- モバイル時のナビゲーション方針

これにより、Skillは「どう整えるか」を担当し、要件テンプレートは「何をどの構成で見せたいか」を担当する形に分離できる可能性がある。

## 保守性・継続開発

v1.1.0では、v1.0.0より見た目と構図の自由度を戻しつつ、Bulma、Bulmaswatch、Bootstrap Iconsという技術基盤は固定できている。

一方、独自CSSが増え、さらにテーマに合わせた独自CSS再実装も確認されたため、「技術基盤が固定されている」だけでは十分ではない。

今後は以下を確認する必要がある。

- 独自CSSの責務がページ固有のものに限定されているか
- テーマ由来の色・タイポグラフィ・標準コンポーネントを再定義していないか
- 別画面でも同じ考え方を再利用できるか
- テーマを変更してもHTML/CSS構造の大部分を維持できるか

## 今回得られた重要な観察

### 1. 禁止を弱めてもAI SaaS風へ直ちに戻るわけではなかった

v1.1.0ではカード利用、独自CSS、レイアウト設計等への制限をv1.0.0より緩めたが、Skill未使用再試行版で見られたグラデーション、発光、ガラス調、強いダークテーマ等は生成されなかった。

### 2. ページ構成の裁量を戻すことで初回完成度が上がった

v1.1.0 Flatly版ではサイドバー、KPI、メイン・サブカラム等をAIが補完し、画面全体としての完成感が向上した。

AIに任せる範囲を「情報構造・レイアウト」と「視覚装飾」で分ける考え方は有効な可能性がある。

### 3. カードは有無ではなく粒度が重要

情報グループ単位でカードを使うことで、平坦さを減らしつつ過剰なカード化も避けられた。

### 4. 独自CSSは量だけでなく責務を見る必要がある

ページ固有レイアウトや状態表現のためのCSSは許容できる一方、テーマの基本色・タイポグラフィ・標準部品まで独自CSSで再実装することは避けたい。

### 5. テーマ指定は正しく反映されたが、テーマの再実装が発生した

Minty指定時にFlatly用の固定色が残る問題は確認されなかった。

一方で、Minty風の色・罫線・文字表現を独自CSS側へ多数定義する傾向が見られた。

### 6. 同一Skillでもレイアウトは揺れる

Flatly版とMinty版ではサイドバー有無を含め、ページ構成が大きく異なった。

この揺らぎはSkill側で固定するより、要件定義側で希望レイアウトを明示できるようにする方が適切と考える。

## 今後の検証課題

今後は以下を確認する。

- v1.1.0を同一要件で再生成した場合も同程度のバランスになるか
- 一般向けサイトやコンテンツサイトでもページ構成の裁量が適切に機能するか
- サイドバーやKPIが不要な画面で、慣例だけを理由に追加されないか
- カード利用を許容したことで、別の要件では再びカード過多にならないか
- 独自CSSが画面ごとに増殖しないか
- Bulma / Bulmaswatchの標準表現を独自CSSで再実装しないよう制御できるか
- テーマ変更時にレイアウトを維持する指定を与えた場合、どの程度安定するか
- 要件定義用プロンプトテンプレートでレイアウト指定を行う方式が有効か
- 複数画面を連続生成した場合に、同一システムとしての統一性を維持できるか

## 現時点の結論

`design_v1.1.0.md` は、v1.0.0で確認された「過剰装飾は抑制できるが、画面が地味・平坦になりすぎる」という課題に対する改善版として、今回のダッシュボードでは良い結果となった。

特にFlatly版では、v1.0.0 Skill未使用・初回版で評価できたページ構成や情報密度に近づきながら、Skill未使用・再試行版で見られた強いAI SaaS風デザインには戻っていない。

一方、追加したMinty検証により、今後の課題も明確になった。

- テーマの標準表現を独自CSSで再実装しすぎないこと
- 大きなテーマカスタマイズはSass等の正式なカスタマイズ工程へ分離すること
- レイアウト希望はSkillへ固定せず、要件定義側で指定可能にすること

今回の結果から、Skillの役割は、

**AIに情報構造とページ構成の裁量を残しながら、技術選定と視覚表現の方向にガードレールを与えること**

と整理するのが現時点では妥当である。

そのうえで今後は、Skillだけですべてを制御するのではなく、

**要件定義で「何を・どの構成で見せるか」を決め、Design Skillで「どう整えるか」を制御する**

という役割分担も検討する。
